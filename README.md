# trade-booking-service

Spring Boot 3 / Java 17 microservice that books securities lending trades, persists them to
PostgreSQL and publishes a `TradeBooked` event to the Kafka topic `trade-events` via a
transactional outbox, so no event is lost when Kafka is unavailable.

## Run locally

Start PostgreSQL and Kafka (KRaft, no ZooKeeper):

```bash
docker compose up -d
```

Run the service on the host:

```bash
mvn spring-boot:run
```

Or run everything, including the service, in Docker:

```bash
docker compose --profile app up -d --build
```

## API

`POST /api/v1/trades`

```bash
curl -i -X POST localhost:8080/api/v1/trades -H 'Content-Type: application/json' -d '{
  "borrower": "Goldman Sachs", "lender": "BlackRock",
  "security": "AAPL", "quantity": 10000, "rate": 0.25, "term": "OPEN", "tradeDate": "2026-11-01"
}'
```

| Status | When |
|---|---|
| 201 Created | Trade booked; body contains the generated `tradeId`, `Location` points to `GET /api/v1/trades/{tradeId}` |
| 400 Bad Request | Validation failure (field-level `violations` array), malformed JSON, or an unknown field such as a client-supplied `tradeId` |

Validation rules: `quantity > 0`, `rate > 0`, all fields required, `security` is an upper-case ticker,
`term` is `OPEN` or a tenor like `30D` / `2W` / `3M` / `1Y`.

`GET /api/v1/trades/{tradeId}` returns a booked trade (400 if not a UUID, 404 if unknown).

### Trade IDs

`tradeId` is generated by the service as an **RFC 9562 UUIDv7** (`com.fasterxml.uuid:java-uuid-generator`),
e.g. `01a194c6-62b5-7f9e-809d-77a767ae1d3f`. UUIDv7 puts a millisecond Unix timestamp in the high
bits followed by random bits, so IDs are globally unique without coordination between instances,
sort by creation time, and keep primary-key index inserts append-mostly (unlike random UUIDv4).
It is stored in a native Postgres `uuid` primary-key column.

## TradeBooked event (transactional outbox)

```
POST /trades ──► ┌─────────── one DB transaction ───────────┐
                 │ INSERT trades   +   INSERT outbox_events │ ──► 201 (Kafka not involved)
                 └──────────────────────────────────────────┘
OutboxRelay (every 500ms) ──► SELECT … FOR UPDATE SKIP LOCKED ──► Kafka send (acks=all) ──► mark published
```

- The trade and its event commit atomically: either both exist or neither does. Booking does not
  depend on Kafka being up.
- `OutboxRelay` publishes pending rows oldest-first, keyed by `tradeId`, with `eventId` and
  `eventType` headers. It stops a batch at the first failure (preserving per-trade order) and backs
  off exponentially (1s → 30s) while Kafka is down, then drains the backlog when it returns.
- `FOR UPDATE SKIP LOCKED` lets multiple service instances run the relay without double-sending.
- Delivery is **at-least-once**: a crash between the Kafka ack and the DB update causes a re-send,
  so consumers should de-duplicate on `eventId`.
- Published rows are purged after `app.outbox.retention` (default 7 days).
- `/actuator/health` reports the backlog as `components.outbox.details.pendingEvents`. It stays UP
  while Kafka is down, since bookings still work.

Payload:

```json
{"eventId":"01a194c6-62d0-7331-b528-dff1f57a4019","eventType":"TradeBooked","occurredAt":"2026-11-01T01:43:11.824Z",
 "tradeId":"01a194c6-62b5-7f9e-809d-77a767ae1d3f","borrower":"Morgan Stanley","lender":"Vanguard",
 "security":"MSFT","quantity":5000,"rate":1.75,"term":"3M","tradeDate":"2026-11-01"}
```

Inspect the outbox:

```bash
docker compose exec postgres psql -U trade -d tradebooking -c "select id, aggregate_id, attempts, published_at, last_error from outbox_events order by created_at desc limit 10"
```

Watch the topic:

```bash
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic trade-events --from-beginning --property print.key=true --property print.headers=true
```

## Logging

Spring Boot's built-in structured logging writes ECS JSON to stdout. Every request gets a
`correlationId` (taken from the `X-Correlation-Id` header, or generated) in the MDC, and domain
fields such as `tradeId` are emitted as top-level JSON keys.

## Configuration

| Env var | Default |
|---|---|
| `DB_URL` | `jdbc:postgresql://localhost:5432/tradebooking` |
| `DB_USERNAME` / `DB_PASSWORD` | `trade` / `trade` |
| `KAFKA_BOOTSTRAP_SERVERS` | `localhost:9092` |

Outbox tuning lives under `app.outbox.*` in `application.yml` (poll interval, batch size, max backoff,
retention). Set `app.outbox.relay.enabled=false` to run an instance that books trades but does not relay.

The schema is managed by Flyway (`src/main/resources/db/migration`), and Hibernate runs with `ddl-auto: validate`.

## Design notes / next steps

- **Client retries:** because the server now assigns `tradeId`, a client that retries after a timeout
  can book the same trade twice. Supporting an `Idempotency-Key` request header (stored with a unique
  constraint) would make retries safe.
- **Higher throughput / lower latency:** at very high volumes, replace the polling relay with
  change data capture (Debezium's outbox event router reading the Postgres WAL).
- Add Testcontainers-based integration tests for the Postgres + Kafka path.
